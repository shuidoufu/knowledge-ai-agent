### Redis 的预热、缓存雪崩、缓存击穿、缓存穿透
1. `**预热**`：系统上线后，提前将相关的缓存数据直接加载到缓存系统。避免在用户请求的时候，先查询数据库，然后再将数据缓存的问题！用户直接查询事先被预热的缓存数据！
2. `**缓存雪崩**`：缓存雪崩是指大量缓存数据在同一时间过期或Redis服务宕机,导致所有请求都直接请求到数据库上，造成数据库瞬时压力过大，可能引发系统整体崩溃。**应对策略**：① <u>可以为缓存设置随机过期时间，避免集中失效;</u>     <u>② 采用多级缓存架构(如本地缓存+Redis);</u>     <u>③ 进行缓存预热，在系统启动时加载常用数据;同时保证Redis的高可用性 0，如使用集群部署。</u>
3. `**缓存击穿**`：单个高热数据过期的瞬间，数据访问量较大，未命中redis后，发起了大量对同一数据的数据库访问，导致对数据库服务器造成压力。**应对策略：① **在<u>业务数据分析与预防方面进行，配合运行监控测试与即时调整策略，毕竟单个key的过期监控难度较高，配合雪崩处理策略即可 </u>**<u><font style="color:#DF2A3F;">② 设置 key 永不过期；③ </font></u>****<u><font style="color:#DF2A3F;">给缓存重建的业务加上互斥锁，缺点是性能低</font></u>**。
4. `**缓存穿透**`：缓存穿透是指查询一个在数据库中也不存在的数据，由于缓存中没有该记录，每次请求都会穿透到数据库，造成数据库压力增大，严重时可能导致系统瘫痪。**应对策略**：① <u>使用布隆过滤器判断数据是否存在，</u><u><font style="color:#DF2A3F;">不存在直接返回</font></u><u>，或者 ② 使用缓存空值，避免频繁访问数据库。</u>

### Redis 哨兵机制是什么，作用是什么？
Redis哨兵机制是一种**高可用性解决方案**，主要用于**监控Redis主从集群，实现自动故障转移**。它能够检测主节点是否宕机，当主节点故障时**自动选举一个从节点升级为新的主节点**，并通知其他从节点和客户端更新配置，从而保障服务的持续可用。

### Redis 集群的脑裂问题
Redis集群在发生网络分区的情况下可能会出现脑裂问题，导致多个主节点同时存在，进而同时提供写服务，从而引发数据不一致。

脑裂时两个主节点都可接受写操作，但彼此无法同步数据，当网络恢复后，其中一个主节点会被降级，其上新增的数据可能丢失，造成整体数据不一致。

`**减少脑裂风险（不可完全避免）**`：可以通过配置`min-slaves-to-write`和`min-slaves-max-lag`参数来降低风险。主节点只有在满足最少从节点数且延迟在允许范围内时才接受写操作。



### Redis 数据过期的删除策略是什么？
Redis数据过期后主要有两种删除策略:定期删除和惰性删除。 

1. 定期删除是指Redis**每隔一段时间**(默认100ms)随机检查部分设置了过期时间的键（每次最多抽取 20 个键判断是否过期），删除其中已过期的键
2. 惰性删除是**<font style="color:#DF2A3F;">在每次访问某个键时，</font>****<u><font style="color:#DF2A3F;">检查该键</font></u>****<font style="color:#DF2A3F;">是否已过期</font>****，若已过期则删除**。这两种策略**<font style="color:#DF2A3F;">结合使用</font>**，兼顾性能与内存回收效率。



### 消息队列设计为推消息还是拉消息？推拉模式的优缺点？
1. **推模式(Push)**是指消息由 Broker主动推送给消费者，消费者被动接收；推模式的优点是**消息实时性高**，Broker接收到消息后可以立即推送给消费者，消费者无需主动查询，使用简单方便。（缺点消费者消费速率低会导致消费者过载）
2. **拉模式(Pull)**是指消费者主动向Broker 发起请求拉取消息。通常讨论的推拉模式是Consumer与Broker之间的交互方式。拉模式的优点是消费者**可以根据自身负载情况控制拉取频率，避免过载**;适合批量拉取，能更合理地进行流量控制和资源调度，Broker实现更轻量、简单。（可能存在消息延迟）

### ~~Redis 中的 PipeLine 功能是什么？（PipeLine 是 Jedis 中的功能）~~
Redis的 Pipeline功能允许**客户端一次性批量发送多个命令到服务端**，而不需要等待每个命令的响应。服务端按顺序执行这些命令，并将结果缓存起来，最后一次性返回给客户端。这种方式减少了网络往返时间和系统调用带来的上下文切换开销，从而显著提升Redis的吞吐量和性能。



### ~~PipeLine 和 Redis 事务有什么区别？~~
**Pipeline**只是优化网络传输的机制，**不保证原子性**，命令会依次执行，即使中间某条失败，其余命令仍会继续执行。而 **Redis**事务通过MULTI和 EXEC命令实现,能保证一组命令的串行化执行，**具备一定的原子性(但不支持回滚)**。若需真正的原子性操作，应使用Lua 脚本。



### 如何解决 Redis 中热点 key 问题？
`**概念**`：热点 Key是指在Redis 中被频繁访问的某个或某些Key，其访问频率或带宽占用远高于其他Key，导致 Redis单节点压力过大，影响整体性能，甚至引发集群负载不均或服务故障。

**解决方法**：

1. 热点Key拆分(分散访问)
2. 多级缓存架构(如本地缓存+Redis)
3. 读写分离(利用主从架构分流读请求)
4. **<font style="color:#DF2A3F;">限流与降级(</font>****<u><font style="color:#DF2A3F;">控制请求量或返回默认值</font></u>****<font style="color:#DF2A3F;">)等。</font>**
