## 什么是消息队列？
1. 消息队列是一种**异步通信机制**，用于在分布式系统中解耦发送发和接收方之间的通信。他通过在消息生产者和消费者之间引入一个**<font style="color:#DF2A3F;">中间缓冲区（broker）</font>**，将消息存储在 broker 中，消费者随后从 broker 中读取并处理消息。
2. 消息队列的**作用**：
    1. **解耦**，消费者和生产者无需同时在线，生产者无需关注消费者，只需要将消息发送到**中间件**中即可，消费者只需从中间件转发消息的队列中获取消息即可；
    2. **削峰填谷**：在高并发时，暂存请求，避免系统过载，等系统稳定后在逐步消费这些消息，实现流量的平滑处理
    3. **异步处理**：将非关键任务异步执行，提升响应速度
3. 消息队列**引入原因**：随着业务不断扩张，系统从单体架构演进到微服务架构，服务数量激增，相互依赖复杂。消息队列应运而生，主要用于实现异步处理、服务解耦和流量控制，提升系统的性能、可维护性和稳定性。

## 消息队列适用于哪些典型的场景，有什么潜在问题？
1. `典型场景`：<font style="color:#DF2A3F;">订单系统的异步处理</font>、<font style="color:#DF2A3F;">日志采集与分析</font>、<font style="color:#DF2A3F;">批量任务调度</font>、数据变更的异步同步等，这些场景都受益于消息队列的异步、解耦和缓冲能力。
2. `问题`：引入消息队列会<font style="color:#DF2A3F;">增加系统复杂性</font>，降低整体可用性，<font style="color:#DF2A3F;">带来消息丢失、重复消费、延迟等问题</font>，同时对运维提出了更高要求，因此需要权衡利弊，根据实际业务需求决定是否引入。



## RabbitMQ 基本架构是什么？哪些核心组件？
1.`**Producer(生产者)**`:就是发件人。负责产生消息并发送给 RabbitMQ。   

2.`**Exchange(交换机)**`:就是快递分拣中心。这是RabbitMQ 最核心的设计!生产者发的包裹从来不会直接投进队列，而是先给交换机。交换机根据包裹上的“地址”(Routing Key)决定把它扔进哪个队列。

3.`**Queue(队列):**`就是快递仓库。消息最终存放的地方，等待被取走。一个消息可以被拷贝到多个队列，但一个队列里的消息只能被消费一次。

4. `**Binding(绑定)**`:就是分拣规则表。它告诉交换机:“如果是发往北京的包裹，请扔进A 队列”。它把 Exchange 和 Queue 连接起来。

5.`**Consumer(消费者)**`:就是收件人。从队列里取出消息并处理。

6.`**Virtual Host(虚拟主机)**`:就是独立租户。这就好比一台物理服务器上跑了多个MySQL 数据库(db1,db2...)。VHost 之间是完全隔离的，互不影响，通常用于区分不同的业务线(比如/order 给订单组用，/user 给用户组用)。



## 常见的 Exchange 交换机类型有哪些？
1. Direct Exchange 直连交换机：按精准的 routingKey 路由键匹配
2. Fanout Exchange 扇出交换机：广播消息到所有绑定的队列中
3. Topic Exchange 主题交换机：支持通配符匹配routingKey 路由键
4. Header Exchange 消息头交换机：基于消息头匹配，较少使用



## RabbitMQ 中无法路由的消息怎样处理？
1. 默认情况下，消息无法找到匹配的队列（没有符合条件的绑定关系），会直接丢弃消息。
2. 防止被丢弃：
    1. **使用备份交换机**：为原始交换机设置备用交换机，如果消息无法正常发送到原始队列中，就将这条消息发送到这个备用交换机，由其进一步路由到指定消息队列进行处理或存储
    2. **使用消息回退机制**：消费者发送消息时设置了 mandatory=true，若消息无法正常路由，rabbitmq 则将消息返回给生产者，生产者可以通过 Return Listener 接收到这些未路由的消息并做相应的处理



## RabbitMQ 中消息什么时候会进入死信交换机？
1. 消息<font style="color:#DF2A3F;">被消费者拒绝</font>(basic.reject或 basic.nack)且 requeue 设置为false
2. 消息或队列的<font style="color:#DF2A3F;">TTL(生存时间)到期，消息未被消费</font>;
3. <font style="color:#DF2A3F;">队列达到最大长度(x-max-length)或最大字节数</font>(x-max-length-bytes)，导致**<font style="color:#DF2A3F;background-color:#FBDE28;">最早的消息被挤出</font>**。

PS：死信交换机无法获取无法路由的消息，死信交换机只接受上去三种情况的消息；

配置死信交换机：x-dead-letter-exchange ，路由键：x-dead-letter-routing-key



## 消息队列如何保证消息不丢失？
需要三个阶段共同配合

1. 生产者：生产者需正确处理 Broker 的响应，做好 try-catch 异常捕获，若收到写入失败等错误，应进行重试，多次失败后触发报警并记录日志。
2. 消费者：在收到消息后，完成业务逻辑后使用 ACK 确认机制，告知 Broker 已成功获取消息并处理业务逻辑（**ACK 确认机制：在收到消息后，再进行业务处理后发送 ACK 确认，防止先发送确认后，突然系统宕机导致消息无法重新投递、从而消息消失**）
3. Broker 中间缓存区：需在消息持久化到磁盘（刷盘 ）或多副本同步完成后才返回相应结果



## 消息队列如何处理消息堆积？
消息堆积是指在消息队列中，消息的生产速度大于消费速度，从而导致大批量数据堆积在队列中无法及时处理。

1. `**第一步 定位消费慢的原因**`，若是 BUG，则处理 BUG，业务逻辑问题就进行优化；同时可以临时扩容增加消费速率
2. `**若消费者消费能力较弱**`，则可以通过 
    1. **增加消费者线程数：提高并发消费能力**
    2. **增加消费者实例：分布式系统中，水平扩展多个消费实实例**
    3. **优化消费者逻辑**
    4. **<font style="color:#DF2A3F;">批量消费</font>****：一次拉取多条数据进行消费，减少网络开销 **
    5. **异步处理提升并发度**
    6. **优化数据库操作，如 sql 优化、批量写入、引入缓存减少 I/O 等待时间**
3. `**限流**`**：在生产者端实施限流，控制消息发送速率，防止消息队列进一步恶化**

##  消息队列中的重复消息（保证消息的幂等性）
1. `**重复消息**`：主要源于网络不稳定和系统可靠性机制。**<font style="color:#DF2A3F;">生产者</font>**发送消息后需等待 Broker 的响应以确认送达，若 broker 已成功写入响应但丢失，生产者会重发消息导致重复；**<font style="color:#DF2A3F;">消费者</font>**在处理完消息后需提交，若此时发生宕机未提交成功，后续重启后会重新消费该消息，导致重复消费。
2. `**消息的幂等性**`：一个操作无论执行多少次，最终的结果都是一致的。

解决方法：    a.  为每条消息分配全局唯一 ID（如 UUID、订单号），消费者在消费前会检查该 ID 是否已经				处理过。

b.通过 Redis 缓存或者数据库去重表 记录已经处理的消息 ID，若存在则跳过，不存在则执行业    务逻辑后记录 ID。

3. `天然幂等性`：业务本身的逻辑，重复执行多次后结果都是一致的，如订单的支付操作

## RabbitMQ 中有哪些主要的工作模式？
1. `简单模式`：生产者将消息发送到队列后，消费者从队列中消费消息，<font style="color:#DF2A3F;">每条消息只能被一个消费者处理</font>。适用于消息量较小、无需复杂路由的对点通信场景
2. `工作队列模式`：<font style="color:#DF2A3F;">多个消费者监听同一个队列</font>，RabbitMQ <font style="color:#DF2A3F;">会轮训的将消息发送给不同的消费者</font>，从而实现任务的复杂均衡，提升处理效率。
3. `发布/订阅模式`：使用 fanout 类型的交换机，将消息广播至所有绑定该交换机的队列中，实现一对多的消息分发，适合日志广播、事件通知等场景。
4. `路由模式`：使用 Direct 交换机，发送消息时，指定路由键，交换机会将消息路由到<font style="color:#DF2A3F;">绑定建与路由键完全匹配的队列中，</font>实现精准的消息分发。
5. `主题模式`：只有 Topic 交换机，支持两种通配符匹配路由键，'*'匹配一个单词，'#'匹配 0 个或多个单词，可以<font style="color:#DF2A3F;">实现路由键和绑定建的模糊匹配</font>，将消息路由到符合的队列中
6. ~~RPC 模式~~：RPC模式中，客户端发送请求消息，并设置reply-to队列和correlation-id;服务器端处理完成后，将响应结果发送回reply-to指定的队列，客户端根据correlation-id 匹配请求与响应，实现同步调用效果,
7. `发布确认模式`：<font style="color:#DF2A3F;">确保生产者发送的消息被 RabbitBroker 成功接收</font>。通过 confirm 模式，broker 会异步返回确认消息，确保消息被正确接收，从而使得生产者不用担心消息是否被成功接收导致重发消息。适用于金融交易、订单处理等可靠性较强的场景。
